NMState manifests

One file per node, each base64-embedded in a MachineConfig and written to /etc/nmstate/openshift/<node>.yml. NMState reads every file under that directory.

Why per-node files

The two control nodes share the same uplink topology (bond0 → VLAN 40 → br-ex) but have different primary IPs on the same L2 segment, so a single shared cluster.yml cannot carry both. Each node gets its own file:

control02.syangsao.net control02-br-ex.yaml 99-control02-br-ex-nmstate 192.168.40.27/24, 169.254.0.2/17 (+ .28/.29 /32)
arbiter.syangsao.net arbiter-br-ex.yaml 99-arbiter-br-ex-nmstate 192.168.40.25/24, 169.254.0.2/17

Rules these files follow

  • MTU declared on every interface (1500, matching current state) — Red Hat requires explicit MTU.
  • Masquerade address preserved: 169.254.0.2/17 is the OVN-Kubernetes masquerade IP; removing it breaks pod egress.
  • Patch port omitted: patch-br-ex_<node>-to-br-int is created by ovn-kubernetes at runtime — listing it in the NMState file would conflict with the OVN controller.
  • Default route not declared: 0.0.0.0/0 via 192.168.40.1 (metric 150) is managed by OVN's configure-ovs routing; it survives the migration and must not be re-declared here.
  • VLANs 60/80/90 untouched: they carry VM data traffic on br-vmdata, outside br-ex's scope.
control02 extra addresses. control02 currently also carries 192.168.40.28/32 and 192.168.40.29/32 on br-ex (likely VIPs for the API/ingress load balancer). They are not included in control02's NMState file because they were added by OVN's routing setup, not by configure-ovs.sh — if they disappear after the migration, re-add them via a NodeNetworkConfigurationPolicy or extend the address list.
